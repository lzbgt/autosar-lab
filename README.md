# AUTOSAR learning lab: virtual tests → real microcontrollers

This project teaches **Automotive Open System Architecture (AUTOSAR) Classic Platform** from real C code and diagnostic traces. Begin on your Arch Linux host; later connect the STM32H723 and AT32M416 as two Electronic Control Units (ECUs) on a Controller Area Network Flexible Data-Rate (CAN FD) bus.

There are **three distinct implementation tracks**, each independently runnable:

- **Small educational controller:** `src/core/` models application behavior, message serialization and diagnostics. Its functions resemble part of AUTOSAR Basic Software (BSW), but are **not** an AUTOSAR-conformant implementation.
- **Actual AutoAS Basic Software (BSW):** `third_party/autoas/` contains real upstream code for communication and diagnostics, built with SCons and AutoAS Python configuration generators. The real `CanApp` and `IsoTpSend` binaries exchange Unified Diagnostic Services (UDS) requests, including a segmented ReadDataByIdentifier response. See [the real-stack walkthrough](docs/11-real-autosar-stack.md).
- **Actual upstream operating system:** Trampoline supplies real Operating System (OS) code with OSEK Implementation Language (OIL) configuration generated by its Trampoline configuration generator (GOIL), then runs tasks through a Portable Operating System Interface (POSIX) virtual processor. The upstream GPL-licensed source is kept separately in `third_party/`.

## Start here — tested commands

~~~sh
cd ~/work/autosar-lab
bash tools/run-all.sh                 # small teaching ECU, host tests and Arm cross compile
bash tools/build-autoas.sh            # actual AutoAS BSW and code generators
python3 tools/test-autoas.py          # real AutoAS CAN/ISO-TP/UDS diagnostics
bash tools/generate-autoas-rte.sh      # upstream Gauge/Telltale SWC ARXML and RTE headers
bash tools/run-trampoline-posix.sh    # real Trampoline OS task/alarm exercise
~~~

These commands have been verified on the Arch host. The small teaching tests use a rootless UDP frame relay. The real AutoAS stack instead uses its upstream UDP-multicast Controller Area Network (CAN) simulator. Neither virtual transport models electrical arbitration, acknowledgment, error frames or physical bit timing. You can also run both real implementations together with `bash tools/run-real-autosar.sh`; source/toolchain locations are listed in [stacks](stacks/README.md) and [toolchains](toolchains/README.md).

If your running Linux kernel provides a working `vcan` driver, use SocketCAN instead:

~~~sh
bash tools/setup-vcan.sh vcan0
python3 tools/smoke.py --backend socketcan --ifname vcan0 --build-dir build
~~~

The current Arch kernel did not expose the `vcan` driver during initial setup. The rootless relay remains the verified alternative.

## Example: follow a value through the software

At the first 100 ms transmit point, ten 10 ms application activations have increased synthetic speed to **50 cm/s**. The signal is encoded little-endian as `32 00` in frame `0x201`:

| Boundary | What it does here or in real AUTOSAR |
| --- | --- |
| Application **Software Component (SWC)** | Produces a typed speed of `50 cm/s` (`src/core/lab_ecu.c`). |
| **Runtime Environment (RTE)** | A generated Runtime Environment (RTE) would connect typed application ports to configured communication services. This repo uses a **handwritten call** instead. |
| AUTOSAR **Communication module (Com)** | Packs the value into message bytes (simplified in `src/core/lab_com.c`). |
| **Protocol Data Unit Router (PduR)** | A real module chooses the next configured destination for the message, rather than changing the signal bits. |
| **Controller Area Network Interface (CanIf)** | A real module maps the outgoing request to a CAN controller and identifier. |
| **Microcontroller Abstraction Layer (MCAL)** | Hardware-specific driver layer within Basic Software (BSW). The physical CAN driver programs the controller registers, transmit queue, filters and error state; **it is not yet present here**. |
| Host transport | `src/platform/lab_transport.c` sends the frame through UDP or Linux SocketCAN, instead of a real microcontroller CAN driver. |

The diagnostic path is separate: a Unified Diagnostic Services (UDS) request `10 03` selects extended diagnostic session. A response `50 03 00 32 01 F4` is carried in an ISO 15765-2 Transport Protocol (ISO-TP) Single Frame. Reading identifier `F1 90` returns a 20-byte payload which the teaching transport divides into First and Consecutive Frames, paced by tester Flow Control. See [the architecture trace](docs/01-architecture.md) and [the byte-level diagnostic walkthrough](docs/03-can-uds-isotp.md).

The guides use **full technical names inline**, rather than making the reader search a glossary. In particular, **Microcontroller Abstraction Layer (MCAL)** is the correct term; “MACL” is a typo.

## File map

| Directory | Contents |
| --- | --- |
| `docs/` | Twelve numbered tutorials: layers, components, ports, scheduling, protocols, diagnostic bytes, real Basic Software (BSW) compilation, debugging and MCU deployment. |
| `src/core/` | Hardware-independent C11 teaching code: runnable, encoded signal, simplified transport and diagnostic state. |
| `src/host/` and `src/platform/` | Linux process and switchable UDP / SocketCAN backend. |
| `src/tests/` and `tools/` | Deterministic tests, frame relay, diagnostic client, cross-compile checks, glossary/link linting and reproducible scripts. |
| `config/` | Educational message identifier `0x201` and diagnostic identifiers `0x7E0`/`0x7E8`. Not generated AUTOSAR configuration. |
| `hardware/` | Board-specific checklists for STM32H723 and AT32M416, including transceiver wiring and CAN FD bring-up. |
| `examples/` | Independent Trampoline and AutoAS exercises; external source remains under ignored `third_party/`. |
| `stacks/` and `toolchains/` | Actual upstream source map, pinned build dependencies, setup and compilation workflow. |

Begin with [docs/00-learning-path.md](docs/00-learning-path.md). Each stage gives commands, expected evidence and explicit limitations.

## Verified stages and limits

| Stage | Evidence |
| --- | --- |
| Virtual controller | Host C unit tests and Classical CAN-format + CAN FD-format UDP frame integration passed. |
| Diagnostic transport | Session control, identifier read, First/Flow Control/Consecutive Frames and negative responses passed. |
| Trampoline real OS | Generated configuration, built the POSIX example, observed nine periodic activations and shutdown. |
| Actual AutoAS Basic Software (BSW) | Built upstream `CanApp`, `libAsOne.so` and `IsoTpSend` with SCons. Verified `10 01 → 50 01 ...`, `10 03 → 50 03 ...`, and 13-byte diagnostic response `22 F1 5B → 62 F1 5B ...` via genuine ISO-TP segmentation. |
| Upstream software-component generation | Ran AutoAS Gauge and Telltale Runtime Environment (RTE) generators: 10 parseable AUTOSAR XML (ARXML) documents and two `Rte_*.h` interface headers. Not linked into the existing host Electronic Control Unit (ECU); ModeSwitchInterface unsupported warning remains. |
| Portability | The core C sources compiled for Arm Cortex-M7 and Cortex-M4 **as objects only**. |
| Physical boards | **Not yet linked, flashed or validated.** Needs exact vendor startup files, Hardware Abstraction Layer (HAL) or genuine AUTOSAR Microcontroller Abstraction Layer (MCAL) ports, pin mappings, CAN FD transceivers and measurements. |
